INTRO:

A long time ago, I found Bill Buzbee’s Magic-1.

And I remember looking at it and thinking: *Wait... you can just build a computer?*

Not assemble one. Not buy a motherboard and put parts into a case. Actually build the thing — down at the logic level.

Then I found Ben Eater. His breadboard CPU, his 6502 computer... and that idea just kind of lived in the back of my head for years.

I wanted to do it.

I also assumed I wasn't technically smart enough to do it.

And, realistically, I didn't have the time anyway.

Then about a year ago, I started building Nitro Core DX, my own fantasy game console. And somewhere along the way that project taught me something pretty important:

With modern tools — and, yeah, a lot of help from AI — I can actually build this stuff.

Which immediately created another problem.

Because I've always wanted to build a computer out of something you can actually *see working.*

Something physical.

Something clicky.

Relays.

So naturally, despite the fact that Nitro Core DX is nowhere near finished — because apparently finishing projects is for other people — I started another one.

This is Relay-65.

The idea is to build a luggable, electromechanical 6502 computer where the CPU's instructions are actually executed by relays.

No microcontroller hiding underneath pretending to be the processor.

When this thing adds two numbers, I want to hear it adding two numbers.

Eventually, I want Relay-65 to become a real little computer: its own console, running Contiki, and — if I can push this ridiculous idea far enough — FUZIX and a tiny web server.

I have absolutely no idea how far I'm going to get.

But we're going to try to build it anyway.

And hopefully, by the end of this, I'll understand computers a hell of a lot better than I did when I started.

ARCHITECTURE (about two minutes)

Okay. So here's how we're actually going to build it.

I already told you it's a 6502 in relays. The question is: why that?

I thought about just using chips. That's the sane 6502. Fast, tidy, already been done, and you never hear it think.

Then I saw relay computers. Relays were practically the original. Before silicon, a computer was a room that clicked.

So obviously I looked at the simplicity of a chip-level machine and thought: what if we made that more complicated, and infinitely louder.

I thought about making *everything* out of relays — memory, serial, the lot. That's how you end up needing a shed, a three-phase outlet, and a divorce attorney.

I thought about a "realer" CPU. Z80. 68000. More swagger. Also more pins, more state, more ways for me to get lost.

6502 won because I can actually understand it. Not just the names of the instructions — the whole little datapath that *does* them. Registers, bus, flags, what LDA actually *is*. I can narrate it.

An 8086 has too many instructions, including a bunch I couldn't explain if you paid me. I'm not starting from a chip I don't understand.

And because, if I'm being unreasonably ambitious, it can run Unix...

Okay. FUZIX.

It's a Unix-like OS that already boots on a 6502. It needs a C compiler, banked RAM, and a disk — which is exactly what we're building the hardware to look like. So when I say this box might serve a web page someday, I mean a slow, clicky, technically functional one. Probably slower than your old 300 baud modem from 1982.

We're not building an entire computer out of relays. We're building the CPU out of relays. The registers, the ALU, the program counter — the parts that actually execute the program. RAM, ROM, serial, later a network card: those can be ordinary chips. Otherwise this thing never leaves the workbench.

Relays are expensive. Cycles are cheap — until they aren't. There's still *one* eight-bit bus and *one* eight-bit ALU. Add, subtract, index, the stack: they all share it. Bumping the program counter used to share it too, and that turned out to be half of every instruction. So we spent extra coils on a dedicated +1 for the PC. Microcode lives in EEPROM; it just tells the relays what to do next. Memory is SRAM and ROM chips, because I am not storing BASIC in a warehouse of coils.

Cards are on a passive backplane. CPU in one set of slots, gadgets in the others. The 6502 only sees a memory map. It does not know, and should not care, what's behind a window.

Last but definitely not least: the software.

Hardware is a very expensive paperweight if nothing runs on it. I did not want a blinkenlight demo. I wanted a prompt. Directories. The feeling that there is a machine under you and it has opinions about where your files live. On a pile of clicky relays. That is an unserious sentence, and I meant every word of it.

So: Unix. The real bit. Processes. A disk. A shell. The kind of operating system that looks at a 6502 and says "sure, I've done worse."

Okay. not Unix... FUZIX.

I am not implementing TCP/IP in clicky gates. The cable out of the box is an ESP32 in a slot — Wi-Fi, Ethernet, whatever it's good at — appearing as a dumb handful of registers. The relay CPU still asks for the bytes. The ESP32 just talks to the internet so I don't have to.

If this works, you'll hear the machine think, and a browser somewhere will load a page that thought came from.

If it doesn't, you'll still hear it think. That's already a win.

HOW IT WORKS:

I said this is a 6502 in relays. That is a useful lie.

There is no 6502 chip in this box. There is a machine that pretends — very slowly — to *be* one.

So: what a 6502 even is, if you never had to care.

It's a little eight-bit brain from 1975. It can remember a handful of bytes: A, X, Y, a stack pointer, some flags, and a sixteen-bit program counter that points at the next instruction in memory. Memory is just addresses. The CPU puts an address out, asks for a byte, and that byte is either "add this," or "jump there," or "the number seven."

That's the whole job. Fetch a byte. Figure out what it meant. Do it. Fetch the next one. Over and over. Serial ports and bank switches are just more addresses. Same bus. Different job.

A real MOS 6502 does that with a PLA and timing tricks baked into silicon. We don't have silicon. We have relays. Relays are terrible at "figure out what it meant." They're pretty good at "copy this byte onto a wire and latch it over there."

So we cheated in the honest direction.

We wrote the whole instruction set down as recipes. Microcode. LDA is not a magic "load A" button. It's a list of tiny jobs: go get the next instruction. Go get the number it asked for. Put that number in A. Do the next one. ADC is the same idea, except somewhere in the list the adder actually adds. JMP is the same idea, except we stop fetching and start pointing somewhere else.

Those recipes live in a cheap memory chip. The chip does not speak 6502. It just turns bits on. This wire. That latch. Add, or don't. The relays do what the bits say. If the bits say copy, something copies. If they say add, you hear it add.

We were cheap about the relays. One bus. One adder. Everything takes turns. We were *so* cheap we were going to bump the program counter on that same adder, every single instruction, all day. Then we counted. Half the machine's life was adding one. So we spent a few extra coils and gave the PC its own +1. Everything else still waits in line.

And it is slow. Relays are metal. Metal has to move, bounce, settle. Call it twenty milliseconds a step if we're being kind. A real 6502 does this in a couple of microseconds. We do it like we're filling out a form in triplicate. Same number in A when we're done. I don't care how long it took. The software shouldn't either.

If we hit an instruction we never wrote, we jam. The lights freeze. That's on purpose. I'd rather see a dead machine than a silent pretend that everything's fine.

That's the computer. We didn't shrink the 6502.

We stretched it out in time until it was small enough to build.

Before we run, we walk.

Making a computer is fantastic. Here's the problem: how do you know the computer works if you don't have software for it? And how do you write software for it if you don't have a computer?

That's where emulation comes in.

I wrote an emulator — with a lot of help from Cursor — of *this* machine. Not a generic 6502 with a coat of paint. It walks the same microcode, the same bus moves, the same format the hardware is supposed to use. If LDA works in the emulator, the relays are supposed to do LDA the same way.

That buys two things.

One: it costs nothing to run. We can get the emulator working, get the software working — Contiki, BASIC, the monitor — before we spend a dime on parts.

Two: when we *do* spend the dime, we have a picture of what should be happening. Same sources, same destinations, same adder, same settle. We can look at the real box and ask: is it doing that, right on time?

If it is, we built the computer.

If it isn't, we know which recipe went wrong — instead of staring at a pile of clicking metal and guessing.

UNIX (then: not quite)

So. Unix.

I said I wanted FUZIX. I meant it. FUZIX is a real Unix-like kernel that already knows how to be a 6502: processes, a disk, `fork`, `exec`, a shell. If the emulator is honest, and the memory map is honest, it should boot the same way the metal will.

And it does.

[ON SCREEN: emulator, WARP, CompactFlash image. Wait for it. Do not type until the prompt.]

That's FUZIX. The monitor copies the kernel off the CF card, the kernel mounts the filesystem, `/init` runs, there's no inittab so it just hands you a shell. `_>` at slash. You can `ls`. You can `cd`. That is a Unix boot on this fake 6502, walking the same microcode the relays are supposed to walk.

I am not going to pretend that was easy. It was a lot of "why is write() hanging" and "why did typing during the IDE scan steal the root device." But it boots. That part of the brag is real.

Now the part that is also real.

Even in the emulator, OVERCLOCK on, WARP, no coil waits — just the computer under the desk chewing through the microcode as fast as it can — FUZIX is still *slow*. You sit there. You wait. The lamps twitch. Eventually a prompt. Then you type `ls` and you wait again. Not "old computer" slow. "Did I freeze it" slow.

That's the emulator *skipping* the physics. The real box does not get to skip the physics.

Each microstep is two coil edges. We pad those to about ten milliseconds apiece so the contacts can actually close. Twenty milliseconds per microstep. I sat there hoping I had the prefix wrong — microseconds, maybe, if we were lucky. We are not lucky. Relays move metal. Metal does not settle in twenty microseconds. If it did, FUZIX would boot in something like twenty, thirty minutes, and I would have a very different video.

Do the math the honest way.

FUZIX wants on the order of fifty to eighty *million* microsteps just to get a shell. At twenty milliseconds each, that is not an afternoon. That is days. One `ls` is another ten, twenty million. You would type a command on Monday and get the listing sometime midweek, assuming nobody bumped the table.

So technically, I can say it: FUZIX can run on this. That part is true. It is also so far from practical that nobody is going to sit there and use it. I needed another option.

Enter Contiki.

Contiki is a tiny OS for computers that barely exist. No Unix kernel. No `fork`. We did not put a TCP stack on the 6502 either — the ESP32 still talks to the network; we just ask it for bytes. What we *did* put on top is a shell that behaves enough like a Unix box that your hands stop arguing.

[ON SCREEN: same emulator, load the Contiki console. Prompt should be almost immediate.]

`_>` at slash. `ls`. `cd www`. `cat`. A cwd in the prompt when you leave root, because otherwise it doesn't feel like a place. BASIC is a program you start and stop, not the whole personality of the machine. `httpd` too. There's a tiny editor for the HTML page that server actually sends.

That is not Unix. I'm not going to put a beard on it and call it Unix.

It is Unix-*like*. You get a prompt. You move around a directory tree. You run a thing, you come back. And on the real relays, at a few instructions per second, that is a computer you can *use* instead of a computer you can *describe*.

FUZIX was the exam. Contiki is the daily driver. Same 6502. Same click. Different amount of life left in the day.
